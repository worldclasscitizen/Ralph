# Ralph Control Center 사용 가이드

Ralph Control Center는 **현재 사용자의 컴퓨터에서 실행 중인 Ralph Loop를 보기 쉽게 보여주는 로컬 관제 대시보드**다. 루프와 별도 프로세스로 실행되며 모델 라우팅, 폴백, 프롬프트 재작성, 검증, 점수 또는 종료 조건을 바꾸지 않는다.

## 언제 사용하는가

- Ralph를 시작하기 전에 `PROMPT.md`의 작업 계약을 화면으로 확인할 때
- 지금 어느 Iteration과 단계가 실행 중인지 확인할 때
- 모델 재시도나 fallback이 발생한 이유와 검증 증거를 확인할 때
- 중간 실패가 다음 반복과 Git checkpoint에 어떤 원인·대응으로 남았는지 확인할 때
- 이전 로컬 run의 Critic 판정, 테스트 로그와 Git checkpoint를 다시 볼 때
- 모델별 담당 작업과 공급자가 보고한 입력·출력 토큰을 비교할 때
- 다음 AI 단계에 반영할 Operator Note를 작성할 때

## 실행 순서

프로젝트 루트에서 두 터미널을 나란히 사용한다.

```bash
# 최초 한 번 또는 업데이트 후: 실행 환경 검사
.ralph/ralph-dashboard.sh --check

# 터미널 1: 대시보드 실행 및 브라우저 열기
.ralph/ralph-dashboard.sh --open
```

```bash
# 터미널 2: 경로와 모델 체인을 먼저 확인한 뒤 Ralph 실행
.ralph/ralph-loop.sh --explain --task <task-id>
.ralph/ralph-loop.sh --task <task-id>
```

기본 주소는 `http://127.0.0.1:7331`이다. 이미 사용 중인 포트라면 `.ralph/ralph-dashboard.sh --port 7444 --open`처럼 바꾼다. 브라우저 상단의 연결 표시가 `LIVE`이면 선택한 실행이 진행 중이며, `CONNECTED`이면 대시보드 스트림은 연결됐지만 선택한 실행은 종료된 상태다.

## 화면 읽는 법

| 표시 | 의미 | 개발자가 할 일 |
|---|---|---|
| 초록 | 해당 단계가 정상 완료됨 | 필요하면 증거를 확인하고 계속 관찰 |
| 파랑 | 현재 실행 중 | 선택한 노드의 최신 출력과 경과를 확인 |
| 노랑 | 재시도, fallback 또는 주의가 필요함 | 모델 시도와 실패 분류를 확인 |
| 빨강 | 단계 또는 run 실패 | Critic·verifier 증거와 터미널 종료 코드를 확인 |
| 회색 | 아직 시작하지 않았거나 과거 형식에 상태가 없음 | 앞 단계 완료를 기다리거나 run 증거를 확인 |

상단의 `작업`은 Ralph task 종류, 폴더 아이콘의 `작업공간`은 실제 프로젝트 폴더, `Git 브랜치`는 현재 branch다. 실행 시각은 `시작 시각`·`종료 시각`과 왼쪽 `Loop history` 목록에서 따로 확인한다. 진행 중인 실행은 종료 시각 대신 `아직 실행 중`으로 표시한다.

왼쪽 `Loop history`에서 로컬 실행을 선택하면 작업명과 상태 사이가 구분되어 보이며, 가운데 단계 노드는 접힌 상태에서 `완료`·`실행 중`·`주의`·`실패`·`대기`만 보여준다. 노드를 누르면 실행 주체, 시도 순번, 이해하기 쉬운 판단·행동 요약, 증거 파일과 최근 이벤트가 펼쳐진다. AI 단계의 실행 주체는 정확한 모델명과 추론 강도이고, Verifier는 `테스트·빌드 자동 검사`, Git checkpoint는 `Git 안전 스크립트`다. 뒤의 두 단계는 AI가 아니라 결정적인 로컬 코드가 수행한다. `증거 파일`은 앱 산출물이 아니라 해당 단계의 모델 응답·판정·검증 로그처럼 판단을 확인할 수 있는 로컬 기록이다. 화면은 모델의 비공개 사고과정을 노출하지 않으며 검증 가능한 정보만 보여준다.

`편집`을 누르면 각 종료 기록 앞에 체크박스와 `선택 삭제`·`전체 삭제`가 나타난다. 여러 기록을 체크해 한 번에 삭제하거나, 현재 실행 중인 기록을 제외한 모든 이력을 정리할 수 있다. 삭제 대상은 `.ralph/runs/<run-id>/`의 모델 응답, Critic·Verifier 로그와 토큰 상세 기록뿐이다. 코드, `progress.txt`, `guardrails.md`와 Git checkpoint 커밋은 삭제하지 않는다. 현재 실행 중인 기록은 선택할 수 없고 서버도 해당 기록이 포함된 일괄 삭제 요청 전체를 거부한다. LOOP HISTORY는 Git에서 제외된 사용자별·프로젝트별 로컬 기록이므로 다른 사용자의 이력에는 영향을 주지 않는다.

`PROMPT.md` 영역은 이번 Loop의 작업 계약을 표시하고, 원문에서 백틱으로 감싼 파일명·명령·식별자는 코드 형태로 구분한다. 의미 없는 점 아이콘 대신 계약 항목 번호를 표시하며, 이전 실행의 `작업 시작 시 재현 절차` 제목은 뜻이 분명한 `작업 전 확인사항`으로 표시한다. 체크박스를 추측으로 완료 처리하지 않으며 명시적인 완료 기록만 반영한다.

Iteration의 `종료 복구 지점`은 정상 종료 뒤 생성한 Git checkpoint다. 반면 Critic·Meta·Worker 실패 뒤 표시되는 `중단 전 안전 복구 지점`은 실패 원인과 당시 변경을 되돌릴 수 있게 저장한 것으로, Iteration 성공이나 Worker 완료를 뜻하지 않는다. Git 안전 검사가 비밀 파일·더러운 기준점·commit 오류 등의 이유로 저장을 막으면 Git checkpoint 노드가 빨간색 실패로 표시된다. 새 실행은 정확한 오류를 `git-checkpoint-<n>.stderr`에 저장한다. `.stderr`는 파일 형식이 아니라 프로그램이 오류·진단 문장을 출력하는 표준 오류 스트림을 보존한 일반 텍스트 로그다. 계측 도입 이전 실행에 이 파일이 없으면 대시보드는 원인을 추정하지 않고 `과거 오류 로그 없음`으로 안내한다.

`파일·Git` 탭에서 `M`은 수정, `A`는 추가, `D`는 삭제, `R`은 이름 변경이다. `??`는 파일이 고장 났다는 뜻이 아니라 아직 `git add`로 추적되지 않은 새 파일이라는 뜻이다. 추가 상태와 `+` 변경량은 초록색, 삭제 상태와 `-` 변경량은 빨간색으로 표시한다.

## Iteration과 통과 기준

기본 `6회`는 반드시 여섯 번 실행한다는 뜻이 아니라 최대 시도 횟수다. Critic은 총점이나 합격 verdict를 임의로 만들지 않고 작업별 항목의 `absent/partial/verified/complete` 수준과 증거를 반환한다. 로컬 `critic_engine.py`가 이를 0/50/80/100% 앵커로 환산하여 총점과 `pass/retry/needs_operator`를 계산한다. 첫 Iteration이라도 Worker·Verifier·Hard Gate·최소 점수 조건이 모두 충족되면 즉시 종료한다. 현재 기본 최소 점수는 85점이다.

`retry`는 Worker가 코드나 증거를 보완할 수 있다는 뜻이다. `needs_operator`는 브라우저·로그인·권한·환경 또는 제품 범위 결정이 필요하거나 같은 실패가 반복되어 자동 루프가 멈췄다는 뜻이다. 동일 실패가 두 번 연속 반복되거나 점수가 두 번 연속 3점 미만으로만 개선되면 비용 폭주를 막기 위해 사용자 확인 상태가 된다.

Post-Critic의 `검증 증거`를 열면 공통·작업별 항목의 획득 점수, 앵커 수준, 판정 이유, 증거와 Hard Gate를 표 형태로 확인하고 필요할 때 원본 JSON을 펼칠 수 있다. `경계 재심`은 점수가 통과선의 ±5점, 즉 기본 설정에서는 80~90점이거나 Hard Gate 판정이 `unknown`일 때만 다른 Critic 모델을 한 번 더 호출하는 방식이다. 명확한 통과·실패에는 추가 호출을 하지 않아 비용을 아낀다. 오프라인 고정 sample 24개는 `python3 .ralph/critic_calibration.py --threshold 85 --margin 5`로 검사하며 유료 모델을 호출하지 않는다.

대시보드의 고정 안내 문구는 `합니다`체를 사용한다. 앞으로 Critic과 Meta-Prompter가 생성해 화면에 전달하는 문장도 `.ralph/CRITIC_RUBRIC.md`와 `.ralph/META_PROMPT.md`의 존댓말 규칙을 따른다. 과거 실행의 원문 증거는 감사 가능성을 위해 내용을 고쳐 쓰지 않으므로 예전 말투가 그대로 보일 수 있다.

상단의 `모델·토큰` 페이지에서는 모델별 수행 단계, 정확한 Model ID·추론 강도, 호출 단위 입력·출력 토큰과 원형 비율 차트를 확인한다. 토큰은 공급자 또는 CLI가 실제 반환한 값만 집계한다. 계측 기능보다 먼저 생성된 과거 Codex run은 `.stderr`의 `tokens used` 총량만 남아 있어 `총량만 기록됨`으로 표시한다. 새 래퍼를 사용하는 GPT·Gemini·Claude·DeepSeek·GLM 호출은 공급자가 구조화된 입력·출력 usage 필드를 반환하면 분리 기록한다. 모델 종류와 관계없이 호출 도구가 총량만 제공하면 입력·출력 비율을 임의로 추정하지 않는다.

## 작업 중 개입

상단의 `오퍼레이터 메모`에 지시를 저장하면 `.ralph/OPERATOR_NOTE.local.md`가 갱신되고 **다음 Critic·Meta-Prompter·Worker 호출부터** 반영된다. 이미 실행 중인 한 번의 모델 호출을 실시간으로 변경하지는 않는다.

- 우선순위나 구현 제약을 추가: Operator Note에 저장
- 현재 호출까지 즉시 중단: Ralph 실행 터미널에서 `Ctrl+C`
- 핵심 목표 또는 완료 조건 변경: 루프를 중단하고 `.ralph/PROMPT.md`를 수정한 뒤 기준 커밋 생성
- 잘못된 완료 작업 복구: 먼저 diff와 checkpoint를 확인하고 `git revert <commit>`을 우선 사용

대시보드를 닫거나 서버가 실패해도 Ralph Loop는 계속 실행된다. 반대로 대시보드에서 Operator Note를 저장하는 행동만 의도적으로 다음 노드 입력에 영향을 준다.

## 데이터와 보안 경계

- 서버는 `127.0.0.1`에만 열리며 다른 사용자의 run이나 원격 서비스를 조회하지 않는다.
- LOOP HISTORY는 현재 프로젝트의 `.ralph/runs/`만 읽으므로 다른 프로젝트의 실행 기록과 합쳐지지 않는다.
- `.ralph/runs/`, `.ralph/state.json`, `.ralph/PROMPT.md`와 Git 상태를 읽어 화면을 구성한다.
- 새 run의 공급자 token usage는 `runs/<run-id>/usage-events.jsonl`에 호출 단위로 기록한다. 사용량 기록 실패는 모델 결과나 Ralph 종료 코드를 바꾸지 않는다.
- 분류된 중간 실패는 run별 `failures.jsonl`에 상세히 남고, 공용 시간순 원장은 `.ralph/progress.txt`에 누적된다. 재사용 가능한 교훈만 `.ralph/guardrails.md`에 중복 없이 추가된다.
- `.env`, 개인 모델 설정과 run 디렉터리 밖 파일은 증거 API로 열 수 없다.
- 화면으로 전달되는 증거에서 비밀값으로 의심되는 패턴을 마스킹한다.
- 이벤트 기록은 best-effort이며 기록 실패가 Ralph의 판단이나 종료 코드를 바꾸지 않는다.

## 문제가 있을 때

```bash
.ralph/ralph-dashboard.sh --check
.ralph/verify-project.sh
```

- 화면이 열리지 않으면 Python 3와 포트 사용 여부를 확인한다.
- 화면은 열렸지만 `CONNECTED`가 아니면 서버를 종료한 뒤 다시 실행한다.
- 오래된 run에 일부 단계가 회색이면 대시보드 이벤트 계측 이전에 생성된 run일 수 있다. 새 Ralph run부터 상세 상태가 기록된다.
- 종료된 run의 마지막 노드가 계속 파랗게 반짝이면 대시보드 서버가 예전 코드로 떠 있을 수 있으므로 서버만 종료하고 다시 실행한다. Ralph Loop 프로세스에는 영향을 주지 않는다.
- 대시보드가 아니라 실제 루프가 멈췄다면 Ralph 실행 터미널의 종료 메시지와 `.ralph/runs/<run-id>/` 증거를 먼저 확인한다.
